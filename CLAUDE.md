# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OPORA — a Ukrainian e-commerce storefront for minimalist furniture (chairs, tables, nightstands, beds). Next.js 16 (App Router, React 19) deployed to Cloudflare Workers via OpenNext. **Supabase (Postgres) is the database**; Cloudflare R2 stores product media. UI copy and most code comments are in Ukrainian.

> The data layer was migrated off Airtable. There is no Airtable code left; `airtable-extensions/` is dead and the external extension is no longer used (CORS is now same-origin).

## Commands

```bash
npm run dev        # local dev server at http://localhost:3000
npm run build      # next build
npm run preview    # build + run on the Cloudflare Workers runtime locally (OpenNext)
npm run deploy     # build + deploy to Cloudflare
npm run cf-typegen # regenerate cloudflare-env.d.ts from wrangler bindings
```

No test suite. `next.config.ts` sets `typescript.ignoreBuildErrors: true`, so TS errors do **not** fail the build — **verify types with `npx tsc --noEmit`** when correctness matters. `npm run lint` (`next lint`) is currently broken under Next 16; rely on `tsc` instead.

## Architecture

### Data layer (`src/lib/supabase/`)
- **`supabase/schema.sql`** is the single source of truth for the Postgres schema (English snake_case columns; Ukrainian meanings in `-- ←` comments). It is run once by hand in the Supabase SQL editor — there is no migrations dir. Additional one-off SQL files live alongside it (`estella.sql`, `catalogs.sql`, `normalize_spec_commas.sql`, `images.sql`, `import_rules.sql`, `drop_variant_quantity.sql`, `long_description.sql`, `long_description_blocks.sql`, `long_description_snippets.sql`, `posts.sql`, `product_accessories.sql`, `accessory_combo_photos.sql`, `product_accessory_max_qty.sql`, `checkbox_options.sql`, `variant_specs.sql`, `variant_visibility.sql`, `product_slug.sql`, `product_seo.sql`) and are also applied manually.
- **Two clients**: `supabaseAdmin()` (`client.ts`) is a server-only service-role singleton used for **all storefront reads and every admin write** — RLS is off, so it must never reach the browser. `supabaseBrowser()` (`browser.ts`) is the anon client used **only** for `/admin` auth (sign in/out).
- Domain services (`products.ts`, `catalog.ts`, `comments.ts`, `banners.ts`, `requests.ts`) resolve relationships with **PostgREST nested selects** (e.g. `variants ( ..., variant_options ( options ( name, value ) ) )`) rather than manual multi-fetch joins. `types.ts` holds hand-maintained domain types (no generated `database.types.ts`). `index.ts` re-exports the whole layer; `src/lib/index.ts` re-exports supabase + r2 + utils + constants.
- Core tables: `products` → `variants` (1:n) → `variant_options` → `options`. **An option's TYPE is read from its `value`, there is no `kind` column** (`supabase/checkbox_options.sql` documents this): hex → colour swatch (`isHexColor`), `Так`/`Ні` → a single checkbox for the whole axis (`isBoolGroup`, values in `src/lib/constants.ts`), anything else → a text chip. The Filters tab creates all three (`+ чекбокс` writes the `Так`/`Ні` pair); a checkbox axis is just a 2-value axis, so ticking it selects another variant and therefore its photos. Checkboxes default to **unchecked**: `sortVariants` (`products.ts`, mirrored in `catalog.ts`) orders `Так`-bearing variants after the rest before `sort_order`, so the first variant — the page's default, and the only one whose media is sent as a prop — is always the unticked one. Product characteristics are per-variant: `variant_specs` → `specs` (migrated off a per-product `product_specs`, now dropped, via `variant_specs.sql`). Plus `banners`, `comments`, `top_products`, `option_filters`, `requests`, `product_accessories` (self-referencing m:n on `products` — curated "buy with" upsells shown via `AccessoryModal.tsx`, managed by the admin editor's Accessories section / `setProductAccessories` action). **Bed accessory-combination photos** (`accessory_combo_photos` → `accessory_combo_images` → `images`, `accessory_combo_photos.sql`) hold one full photo set per (bed × `imageGroupKey` × accessory-upgrade combination): selecting e.g. «шухляди ЛДСП 102 + велика планка» **replaces** the bed's gallery with photos of it installed. The combo key is built by `src/lib/accessoryCombo.ts` from `accessoryProductId:qty:<value on the accessory's combo axis>` per selected accessory. **`products.combo_axis` names which of an accessory's OWN option axes swaps the host's photos** («Короб» for Шухляда, «Розмір» for Планка безпеки); everything else about the accessory (its colour, material, own size) deliberately never moves the host gallery. It is **discovered, not configured**: `resolveComboForConfig` searches every axis of every linked accessory and the one whose value the upgrade-folder name matched IS the upgrade axis (verified unambiguous across the real catalogue — no folder name matches two axes of one accessory), then the importer persists it via `setAccessoryComboAxis` and later imports search only that axis. A name-based rule could not work: «Розмір» is the upgrade axis for a rail (134см/96см) but not for a drawer (190см/200см follows the bed). Keyed by the accessory **product** (not the `product_accessories` link, so one resolved combo is valid for every bed), and **quantity is in the key** because «Нота Бене» ships 1-/2-/4-drawer shots of the same option — but the lookup falls back to `comboKeyIgnoringQty` when no exact set exists, so a bed photographed with just «з шухлядами» keeps those photos when the customer picks 2. The **same accessory product may be linked twice** (Лаос offers a small *and* a large «Планка безпеки» — one product, two option values), so `product_accessories` has no uniqueness on `(product_id, accessory_product_id)` and `setProductAccessories` replaces the list wholesale; `comboKeyOf` merges parts sharing an accessory+quantity into one `+`-joined entry, which is what makes the storefront's two separate selections produce the identical key the importer wrote from one folder. Picking an accessory variant also **mirrors its «Матеріал» onto the bed** (`MIRRORED_AXIS` in `ProductDetailClient`): the set is built in one wood, and last choice wins. Only that axis — colour must never move the gallery. `scripts/check-accessory-combo.mjs` asserts all of this. Managed in the product editor's «Фото комбінацій аксесуарів» section (`AccessoryComboPhotosSection.tsx` → `api/products/media/accessory-combo`), which offers both per-combination upload and a **bulk folder import**: `parseBedCombos` (`src/lib/estella/folderImport.ts`) is the mirror of `parseBedsFolder` — it keeps exactly the config (upgrade) folders that one throws away, buckets them by packaging and by Матеріал+Колір+«З білими ніжками» into the same `imageGroupKey` the plain photos use, and `bedConfigParts` maps the folder text to accessory option values (велика→134 / мала→96, but **positionally**: everything after «одинарн» is a single rail 130-140/70-80; a leading count is the drawer quantity). Matching is by option-VALUE pattern, so one rule resolves both which accessory and which of its options; a pattern matching several values (Лаос: «одинарна мала планка» is both 70см and 80см) links one upload to every matching combo via the route's `comboKeys` array. Two traps the real data exposed: the white-legs branch is shot in a **two-tone colour code** (171-180 = base + Білий) while the DB encodes the white part as the checkbox, so `parseBedCombos` drops the Білий component there or the group key matches no variant; and upgrade folders can carry a **drawer count** («З 4 шухлядами ЛДСП 102») which is the accessory quantity, not another option. `scripts/check-bed-combos.mjs` asserts this against the real `~/Downloads/BEDS` layout (7788 photos → 2290 sets, 48 upgrade names). This replaced an earlier unfinished per-link `postillya/karkas/matrats_image_id` triplet, which ignored which option was selected. `variants.visible` (bool, default true) hides a variant from the storefront option selector without deleting it (a manual admin-curation flag; the importers no longer write `false`). Storefront filter taxonomy is DB-backed: top-level `catalogs` and `subcategory_options` (subcatalogs linked to a catalog by NAME); `catalog.ts` resolves these via `getCatalogs`/`getSubcatalogs`/`getFilteredCatalog`/`getFilterOptions`.
- **Product images are normalized** (`images.sql`): `images` (deduped R2 URLs) ↔ `variants` via `variant_images` (m:n), replacing the legacy per-variant `photos[]`/`photos_compressed[]` arrays (empty in all 4387 variants — the storefront no longer reads them; the columns still exist and can be dropped by hand). `images.url_compressed` is always `url` with `/images/` → `/images-compressed/` + `.webp` (verified across all 24245 rows), which `products.ts` exploits to keep the cached product payload small. Only **Матеріал** and **Колір** change how a product looks — variants differing only by Розмір/Відстань між ламелями share the same photos. `imageGroups.ts` (`isVisualOption`/`imageGroupKey`) is the single source of truth for that grouping; used by the upload route (propagate to siblings) and the **image-dedup** admin tab (`(panel)/image-dedup/`, «Дублікати фото» — merges duplicate photos into one shared record and deletes extra R2 copies, idempotent).
- **`products.long_description`** is a **`jsonb` array of typed content blocks** (`LongDescriptionBlock[]`, `src/lib/longDescription/types.ts`) — the per-product "big description" shown full-width on the product page. It replaced a free-form Markdown+HTML blob edited with `@mdxeditor/editor` (removed in 9fafcdb): because every product's description is laid out differently, the admin **composes** it from a fixed library of Tailwind section components (heading, paragraph, callout, table, imageText, colorSwatches, gallery, plus `columns` for side-by-side rows and `snippet` for shared blocks) instead of authoring HTML. Text fields (paragraph/callout text, intros, captions, **table cells**) go through `react-markdown` + `remark-gfm`, so `**bold**`, `[links](url)` and `~~strikethrough~~` (old→new prices) work with no extra fields and **no raw HTML**. `src/components/longDescription/LongDescriptionRenderer.tsx` is the single renderer, used **both** by the storefront (`ProductDetailClient.tsx`, full-width above `<Reviews>`) and by the admin builder's live preview, so there is one source of styling. `LongDescriptionBuilder.tsx` (admin product editor) does add/delete/reorder + per-block field forms; block image uploads POST to `api/products/media/content-image` — a plain one-off R2 upload (unlike the variant-relational, deduped `media/images` route) returning a public URL. Every block field is plain text/URL rendered through typed props, so **no markdown parsing or HTML sanitization is involved** (safe by construction). Adding a block type = add a variant to the union + a case in the renderer + a case in the builder's `BlockFields`/`blankBlock`. **Never add a PDF/file-download block** — assembly PDFs belong to `assembly_pdf_url` and the «Збірка» accordion. **Shared blocks** (`long_description_snippets` table, `long_description_snippets.sql`, admin tab `(panel)/description-blocks/` «Спільні блоки») are edited once and live-referenced by many products: a product stores `{type:"snippet",snippetId}`, and `resolveProductSnippets` in `products.ts` inlines the content **before** `unstable_cache` writes, so snippet edits need `bump()` (the snippet actions do this) to show up. Snippets nested inside snippets are not resolved — the builder doesn't offer `snippet`/`columns` inside a `columns` child for that reason.
- **Informational articles** (`posts` table, `posts.sql`, admin tab `(panel)/posts/` «Статті», public route `app/posts/[slug]/`) reuse the *same* `LongDescriptionBlock[]` body, builder and renderer as product descriptions — an article is just blocks plus `slug`/`title`/`excerpt`/`visible`. Product descriptions link to them with **relative** markdown links (`[текст](/posts/<slug>)`): the renderer's `Anchor` sends `/`-prefixed hrefs through `next/link` in the same tab and everything else to a new tab, so **the same content works unchanged on localhost and production** — never author absolute URLs with a hardcoded domain. `savePost` validates the slug (`^[a-z0-9]+(-[a-z0-9]+)*$`) and reports the unique-violation on `slug` in Ukrainian. Articles are listed in `sitemap.ts` chunk 0.
- **`products.slug`** (`product_slug.sql`, optional, unique on `lower(slug)`) is a human URL set by hand in the product editor — `/catalog/Vega` instead of `/catalog/<uuid>`. Lookup is `byIdOrSlug` (`supabase/client.ts`), used by both `fetchProductById` and the admin `getProductFull`: a UUID-shaped param filters on `id` with `eq`, anything else on `slug` with `ilike` (case-insensitive URLs), and a param matching **neither** regex returns null → 404. That regex guard is **load-bearing, not cosmetic** — `ilike` treats `%`/`_` as wildcards, so `/catalog/%` would otherwise return an arbitrary product. Every product link is built by **`productRef`/`productHref` (`src/lib/utils.ts`)** — slug when set, UUID otherwise — and there are no hand-built `/catalog/${id}` literals left: `catalog.ts`, `search.ts`, `getMultipleProductsWithVariations`, `TopProducts`, `AccessoryModal`, the recently-viewed card, `sitemap.ts` (via `getProductRefs`, renamed from `getProductIds` **with a new cache key** so stale entries don't serve UUID-only lists) and the admin `ProductsTable` all go through it, so a `slug` column must stay in each of their select strings or links silently fall back to UUIDs. `/catalog/[slug]/page.tsx` builds `canonical` + JSON-LD from `productHref(product)`, **not** the route param — both spellings resolve, so Google must be told which one is primary. Because the UUID path stays live, setting or changing a slug breaks nothing already in the wild (shared links, `/catalog/<uuid>` hrefs persisted in visitors' «Ви раніше переглядали» localStorage). `scripts/check-product-ref.mjs` asserts the wildcard guard, the slug-vs-UUID precedence, and that what `productHref` emits is what the lookup accepts.
- **`products.seo_title` / `seo_description`** (`product_seo.sql`, both optional) are per-product overrides edited in the product editor's «SEO» card. `generateMetadata` (`catalog/[slug]/page.tsx`) falls back to the existing derivation when they're blank (title = model, description = «Від &lt;ціна&gt; ₴`), so an empty column changes nothing. A set title is emitted as **`title: { absolute }`** — the root `template: "%s | OPORA"` must not append to a hand-written title, since SERPs cut at ~60 chars. They ride inside the `unstable_cache`d product payload, so edits need the `bump()` that `saveProduct` already does. No OG-image override: the first variant photo is already the right preview image.
- Because SQL is applied **by hand**, new-table reads go through `isMissingTable(error)` (`supabase/client.ts`, matches PostgREST `PGRST205` + Postgres `42P01`) so code deployed before its table degrades to an empty list / 404 instead of breaking. This matters most for `listSnippets`, which the **product editor page** calls — without the guard, an un-migrated DB would make every product uneditable. `search_tsvector.sql` deliberately excludes this column from full-text search. Both read paths guard with `Array.isArray` since the `text`→`jsonb` migration (`long_description_blocks.sql`) is applied by hand.

### Rendering & caching
- Pages under `src/app/` are **Server Components** reading Supabase directly; interactive parts split into `*Client.tsx` Client Components (e.g. `CatalogClient.tsx`, `ProductDetailClient.tsx`).
- **The product page does not ship every variant's media to the browser.** The server keeps the full `ProductDetail` (metadata + JSON-LD need it), but `clientProduct.ts` (`toClientProduct`) strips `images`/`imagesCompressed`/`specifications` off the main variants — a bed has 1000 of them, which was 1.5MB of HTML. Only the first variant's media goes as the `initialMedia` prop; the rest is fetched per variant from the public `api/products/variant/[variantId]` route (`getVariantMedia`, ~1.4KB, KV-cached) by `useVariantMedia`, prefetched on option hover. Client types split accordingly in `components/types.ts`: `VariantSummary` (selector data) + `VariantMedia` (photos/specs) = `Variant`, and **accessory** variants stay full `Variant`s (only ~280 per bed, so the accessory modal needs no requests). `toCardVariations` builds the deduped «Ви раніше переглядали» card — that entry goes into `localStorage`, so it must stay small.
- Storefront reads are wrapped in `unstable_cache(..., { revalidate: 3600, tags: ["catalog"] })` (see `catalog.ts`). **Every admin mutation must purge this** — actions call `bump()` (defined in `admin/actions/_shared.ts`) = `updateTag("catalog")` + `revalidatePath("/admin")` after each write.
- **On Cloudflare, `unstable_cache` only works if OpenNext has a cache store.** `open-next.config.ts` wires `kvIncrementalCache` + `kvTagCache` to the `NEXT_INC_CACHE_KV` / `NEXT_TAG_CACHE_KV` bindings in `wrangler.jsonc`; without them the default override discards everything and every request re-queries Supabase (that was the cause of Cloudflare **error 1102**, worker over resource limits). KV is eventually consistent, so admin edits land within ~60s instead of instantly.
- **Next drops any cache entry over 2MB, silently.** Two hot paths are shaped to stay under it: `fetchCatalogBase` keeps one variation per `imageGroupKey` × 2 photos (~0.2MB, was 7.1MB per request), and `fetchProductById` caches a packed `PackedDetail` — originals only (compressed URLs derived by rule) plus deduped spec sets — which `unpackDetail` expands back to the untouched `ProductDetail` shape after the cache read (~1.2MB for a 1000-variant bed, was 2.09MB and therefore uncacheable). **If you add fields to either, re-measure.** Client data fetching uses **TanStack Query** (`providers.tsx`, wraps the whole app).
- **Comparison** (`/compare`, `app/compare/`): compares **variants**, not products. The list is **in the URL** (`?ids=<variant uuids>`, built/parsed by `src/lib/compare.ts`), so any link opens for anyone; `localStorage` (`store/compareStore.ts`, key `opora-compare-storage`) only holds the visitor's own `{id, catalog}` list — bare `/compare` redirects to it, a foreign link shows a «Зберегти» banner (or is adopted when the own list is empty). Max `MAX_COMPARE_ITEMS` = 4, one catalog only — enforced in the store's `add` **and** on the server (`getCompareVariants`: the first variant's catalog wins, since the URL is hand-editable). Server data is cached **per variant** (`getCompareVariant`), never per list. The «Додати до порівняння» button is `CompareButton` in the BuyBox (adds the active variant); the header shows a count badge. Photos use `ImageSlider` (the product page's mobile slider, extracted from `ProductGallery`) + `FullscreenGallery` via `useFullscreenGallery` (shared with `ProductDetailClient`).
- Cart is global client state via **Zustand** with `persist` to localStorage (key `opora-cart-storage`); only `items` is persisted so the cart doesn't reopen on reload (`store/cartStore.ts`).

### Admin panel (`src/app/admin/`)
- Route group `(panel)/` = the authed dashboard; `login/page.tsx` is public. `layout.tsx` holds the sidebar `NAV` array — add a tab by adding an entry + a folder. The sidebar is **grouped, not one flat list**: everyday tabs (products, marketing, comments, requests, catalogs, description-blocks, posts) come first, then a divider (`divider: true` on the NAV entry) and a single **«Розробка»** tab (`(panel)/dev/`) holding the one-off/maintenance tools. `marketing/` and `dev/` are **composite pages** — they own no manager of their own, they render the neighbouring folders' components inside `<Tabs>` from `admin/ui.tsx` (`banners/BannersManager`, `filters/FiltersManager`; `import/ImportPanel`, `tables/TablesPanel`, `estella/EstellaClient`, `image-dedup/ImageDedupClient`), so those folders keep their components but no longer have a `page.tsx`. `Tabs` seeds the active tab from `?tab=` (dashboard cards deep-link that way) but switches with **local state + `history.replaceState`** — `router.push` re-ran the `force-dynamic` server page on every click, which was visibly laggy. Tabs mount on first open and then stay mounted behind `hidden`, so switching back doesn't refetch, but Estella doesn't fire its offers query until you actually open it.
- **All CRUD is Next.js Server Actions in `admin/actions/`** (not per-entity REST routes) — one file per entity (`products.ts`, `variants.ts`, `banners.ts`, …) re-exported from `actions/index.ts`; shared `db()`/`bump()` live in `actions/_shared.ts`. `ui.tsx` is a tiny custom Tailwind component kit (`Button/Input/Card/Field/Badge/Checkbox`) — use it, there is no external UI library. Brand color is `opora-brown`.
- **Auth is enforced in `src/middleware.ts`** (Next.js middleware). It gates `/admin/*`, `/api/admin/*`, and R2 media write routes (`/api/products/media`, `/api/banners/media`) behind a Supabase Auth cookie session — a single shared admin login, no roles. Public APIs (requests/telegram/novaposhta/comments/products reads) are deliberately not matched.

### Data imports (three pipelines, all under the admin panel)
- **CSV** (`(panel)/import/` → `api/admin/import/route.ts`): one-time migration of the old Airtable export. Table detected by filename substring; parsed client-side with PapaParse; POSTed as row arrays. The route is thin — per-entity import logic lives in `src/lib/importer/` (`csvImporters.ts` + `parse.ts` cell coercers).
- **Estella XML** (`(panel)/estella/` → `api/admin/estella/route.ts`): ongoing supplier feed. The huge `estella_all.xml` is parsed **in the browser** (native `DOMParser`) and streamed in batches into the `estella_offers` **staging table**; `estella_DATE.xml` flips matching `Id`s to available. A cursor-paginated/searchable admin list then **promotes** staged offers into `products`/`variants` (grouped by product `name`, one variant per offer, `Колір` → color option via `src/lib/estella/colors.ts`, other params → `variant_specs`). Route stays thin — staging/promotion logic is in `src/lib/estella/` (`stagingService.ts`, `promoteService.ts`, `offers.ts`). Promotion runs in 100-offer chunks the client loops over (bounds Cloudflare Workers subrequests) and is idempotent (existing-SKU guard + `imported` flag).
- **Estella folder import** (`src/lib/estella/folderImport.ts`): pick one local folder of product photos → one product; each leaf folder beneath it is a variant. Color options are parsed from filenames (3-digit codes → `colors.ts`, two-tone codes yield 2 options), the leaf folder name becomes the Матеріал option. **Beds get a dedicated constructor mode** (`parseBedsFolder`/`deriveBedVariant`): folder depth varies (1–3 levels between model and material leaf) and Каркас/З матрацом/З постіллю live in sibling folders — those are merged into one variant's photos (ordered by packaging) rather than split into separate variants, with Матеріал/Колір + «З білими ніжками» as the variant-identity axes. A **«… з білими ніжками» folder branch is the same product**, not another model: the phrase is stripped from the model name and becomes the `З білими ніжками` **checkbox option** — otherwise both branches attached to the same XML offers and their photos merged onto one variant (6 photos instead of 3). Every variant of such a product gets an explicit `Так`/`Ні` value, because `matchesSelection` ignores axes a variant has no option for, so a partial axis resolves every choice onto the plain bed; products with no white-legs branch get no axis at all. A **«… односпальне» folder stays its own product** (unlike white legs), and since the Ліжка catalog's `splitRule` splits the XML at `maxWidth: 90`, `parseBedsFolder` tags such a pair with `sizeBand` (`single` ≤ 90 / `double` > 90) and `offersFor` filters the attached offers by it — otherwise the single bed's photos also landed on the double bed's variants (one folder product attached to all 24 sizes). A bed with no «односпальне» sibling gets no `sizeBand` and keeps every size. `scripts/check-beds-folder.mjs` asserts all of this on the real folder layout (esbuild-bundles the modules, no test runner). **Upgrade (config) folders are skipped entirely** — `parseBedsFolder` drops any file whose folder chain has a config level, so only the plain bed's 3 packaging photos reach R2/the DB; the upgrade photos are uploaded by hand per combination in the admin editor instead (`accessory_combo_photos`, see the Data layer section). XML characteristics (`variant_specs`) are copied from each promoted offer variant onto its size/lamels/config clones, so every variant carries the same specs — not just the first.
- **Import rules** (`estella_catalog_rules` table via `import_rules.sql`; `src/lib/estella/catalogRules.ts`; `(panel)/import` rules manager): per-catalog, DB-configurable `OptionRule[]`/`SplitRule` that extract extra options (e.g. Коліщатка, Відстань між ламелями) and split variants during import — replacing what used to be hardcoded. Catalogs are the 6 hardcoded names in `ESTELLA_CATALOGS`, matched from the product name by `detectCatalog`.

### Integrations
- **R2** (`src/lib/r2/`, `api/products/media/`): S3-compatible client; images transcoded to WebP; media served from `*.r2.dev` (allowed in `next.config.ts` `images.remotePatterns`). Product photos are actually delivered through **Cloudflare Image Transformations** (`/cdn-cgi/image/...`, `toCfImageUrl` in `utils.ts`) — edge-side `format=auto` (AVIF) + a fixed width/quality, wrapping the already-compressed R2 URL; `OptimizedImage` (`components/ui/`) catches transform errors (quota exhausted, or localhost where `/cdn-cgi` doesn't exist) and falls back to the plain R2 URL. Width/quality are constants so each photo is one transformation, not one per responsive breakpoint (free tier is 5000 unique transformations/month). Requires the Cloudflare dashboard's Transformations toggle + R2 host allow-listed under Specified origins — already done, but a fresh zone needs it repeated. `scripts/check-cf-image.mjs` asserts the URL construction.
- **Nova Poshta** (`src/lib/novaposhta/`, `api/novaposhta/`): city/warehouse lookup for checkout. **Telegram** (`api/telegram/`, message formatting in `src/lib/telegram/formatOrderMessage.ts`): order/lead notifications. **Analytics** (`src/lib/analytics/umami.ts`): `trackEvent()` is a safe no-op wrapper around `window.umami`; GA via `NEXT_PUBLIC_GA_ID`. **SEO**: `src/lib/site.ts` centralizes `SITE_*`/`STORE`; consumed by `app/sitemap.ts`, `robots.ts`, `components/seo/JsonLd.tsx`.

### Path alias
`@/*` → `src/*` (see `tsconfig.json`).

### Mobile styling (required)
**Every new component and page must be styled for mobile**, storefront and admin alike — not desktop-only with mobile left for later. Write Tailwind **mobile-first** like the rest of the codebase: unprefixed classes are the phone layout, `md:` (the main breakpoint here) and `lg:` layer the desktop layout on top. Check the result at ~375px width (no horizontal overflow, tap targets ≥ 44px, text readable without zoom, modals/drawers fit the viewport) before calling the work done.


## Deployment & environment

Deployed as a Cloudflare Worker via `@opennextjs/cloudflare` (`wrangler.jsonc`, `open-next.config.ts`). Bindings (`ASSETS`, `IMAGES`, `WORKER_SELF_REFERENCE`) are typed into the committed `cloudflare-env.d.ts` via `npm run cf-typegen`.

Required env vars (local dev: `.env`/`.env.local`/`.dev.vars`; see `.env.example`): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `CLOUDFLARE_R2_API_URL`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `NOVA_POSHTA_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_GA_ID`, `NEXT_PUBLIC_UMAMI_WEBSITE_ID`.
